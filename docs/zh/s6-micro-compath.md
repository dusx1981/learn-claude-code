`micro_compact` 函数的压缩策略之所以有效，是因为它基于对话上下文管理的几个关键假设和权衡，能够在显著减少 token 消耗的同时，尽量保持模型对对话历史的理解能力。下面详细解释其原理。

---

## 1. 对话上下文的长度限制

大语言模型（如 GPT 系列）有固定的上下文窗口（例如 8k、32k、128k token）。在包含多次工具调用的对话中，**工具结果（`tool` 角色的消息）通常包含大量文本**（例如 API 返回的详细数据、长文本输出），它们会快速填满上下文窗口，导致后续消息被截断或需要丢弃较早的内容。

---

## 2. 压缩的核心思想

`micro_compact` 采取以下策略：

- **保留最近的 `KEEP_RECENT` 条完整工具结果**：假设**越近的工具结果对当前对话的重要性越高**。例如，用户刚刚查询的天气结果可能马上会用于后续讨论，而几轮前的查询结果已经不再需要。
- **将更早的工具结果内容替换为简短占位符**：占位符格式为 `"[Previous: used {tool_name}]"`，仅保留工具名称。
- **保留所有工具调用请求（`assistant` 的 `tool_calls`）**：这些消息通常较小（只包含函数名和参数），它们让模型知道历史上发生过哪些工具调用。

---

## 3. 为什么这样压缩有效？

### 3.1 保留关键元信息
- **工具名称**：占位符中包含工具名称，模型可以知道“之前调用过什么工具”，但不知道具体返回结果。这有助于模型理解对话流程（例如“用户之前让我查过天气”），而不需要知道具体数值。
- **工具调用记录**：所有 `tool_calls` 消息都保留，模型能看清调用顺序和参数，这对理解用户意图和后续推理至关重要。

### 3.2 减少 token 消耗
假设一条工具结果原本有 1000 token，压缩后变成约 5 token（例如 `[Previous: used get_weather]`）。如果对话中有 10 条旧结果，压缩后可以减少近 10,000 token，释放大量空间给新消息和最近的结果。

### 3.3 符合对话的局部性
在多数对话场景中，**用户通常只关心最近几轮交互的结果**。例如：
- 用户先问“北京天气”，得到详细预报。
- 接着问“上海呢？”，得到上海天气。
- 然后问“对比一下两地温度”，此时需要两个结果都在上下文中。
但如果用户继续问“明天深圳天气如何？”，前两个城市的详细数据就不再必要，模型只需知道“之前查过北京和上海”即可，而不需要具体数值。

### 3.4 模型仍能利用上下文连贯性
由于 `tool_calls` 消息保留，模型能识别工具调用历史。压缩后的占位符也明确提示“之前用过该工具”，因此模型在回答时仍能保持对话的连贯性（例如可以说“正如我们之前用天气工具查过的那样”）。但若后续需要依赖旧结果的精确数据（如“北京昨天的温度是多少”），模型可能无法提供，因为数据已被压缩。这恰好符合**近期信息优先**的假设——如果用户真需要旧数据，通常会重新查询。

---

## 4. 示例对比

### 压缩前（大量 token）
```
assistant: 调用 get_weather(city=北京)
tool: 北京今天晴，25℃，湿度50%，空气质量良好...（500 token）
assistant: 调用 get_stock(symbol=AAPL)
tool: 苹果股价150.32美元，涨0.5%...（500 token）
assistant: 调用 get_weather(city=上海)
tool: 上海多云，22℃，湿度80%...（500 token）
user: 北京和上海哪里更热？
```

此时上下文包含三条完整结果，共约 1500 token。

### 压缩后（KEEP_RECENT=1，保留最后一条）
```
assistant: 调用 get_weather(city=北京)
tool: [Previous: used get_weather]          # 5 token
assistant: 调用 get_stock(symbol=AAPL)
tool: [Previous: used get_stock]            # 5 token
assistant: 调用 get_weather(city=上海)
tool: 上海多云，22℃，湿度80%...（500 token）
user: 北京和上海哪里更热？
```

压缩后，前两条结果只占 10 token，总 token 从约 1500 降至约 510。模型仍能看到“北京用过天气工具”，但不知道具体数据，因此在回答“哪里更热”时，只能依据上海的数据和“北京用过天气”这个事实，可能会说“上海气温22℃，北京之前查过，但具体数值已省略，建议重新查询北京天气”。如果用户确实需要比较，可以重新触发查询。

---

## 5. 适用场景与局限性

- **适用**：工具结果较长、对话轮次多、且对最近信息依赖强的场景，如多轮数据查询、逐步对话。
- **不适用**：需要长期记忆所有历史工具结果的场景（如数据分析报告、法律文书），此时应保留完整结果或使用外部记忆存储。

---

## 总结

`micro_compact` 通过**保留最近工具结果、压缩早期结果、保留调用记录**，在上下文长度受限时实现了有效的 token 压缩，同时尽量维持对话的连贯性。这是一种实用的工程权衡，广泛应用于需要管理长对话的 AI 应用中。
